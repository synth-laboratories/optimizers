Better GEPA Python SDK API sketch

Problem

The current Python import shape makes GEPA look like the run itself:

    from synth_optimizers import GepaRun
    GepaRun.from_toml("gepa.toml").execute()

That is backwards for the SDK we want. "Run" should be the generic execution
abstraction. GEPA should provide an optimizer-specific configuration object that
can be loaded, inspected, edited, validated, serialized, and then passed to the
generic runner.

Target shape

    from synth_optimizers import OptimizerRun
    from synth_optimizers.gepa import GepaConfig

    config = GepaConfig.from_toml("gepa.toml")
    result = OptimizerRun(config).execute()

Equivalent explicit construction:

    from synth_optimizers import OptimizerRun
    from synth_optimizers.gepa import (
        GepaConfig,
        GepaBudgetConfig,
        GepaPipeline,
        PromptProgram,
        ContainerConnection,
        DatasetSplit,
        PolicyConfig,
        ProposerConfig,
    )
    from synth_containers import ContainerRunner

    handle = ContainerRunner.from_command(
        ["python", "banking77_synth_gepa_dev.py", "--serve"]
    ).start()
    config = GepaConfig(
        run_id="banking77_dev",
        output_dir="runs/banking77_dev",
        container=ContainerConnection.from_handle(handle),
        dataset=DatasetSplit(
            train_split="train",
            heldout_split="test",
            train_ids=list(range(12)),
            heldout_ids=list(range(4)),
        ),
        program=PromptProgram(
            target_modules=["banking77_classifier"],
            seed={
                "banking77_classifier": (
                    "Classify the customer banking query into exactly one "
                    "Banking77 intent. Return only the label."
                )
            },
        ),
        policy=PolicyConfig.openai(model="gpt-4.1-nano"),
        proposer=ProposerConfig.codex_app_server(model="gpt-5.4-nano"),
        budgets=GepaBudgetConfig(train_rollouts=80, heldout_rollouts=16),
        pipeline=GepaPipeline(
            max_generations=2,
            proposals_per_generation=4,
            minibatch_size=4,
            rollout_workers=8,
            max_in_flight_candidates=4,
        ),
    )

    config.validate()
    config.to_toml("gepa.generated.toml")
    result = OptimizerRun(config).execute()

Core abstractions

Hierarchical config model

`GepaConfig` should not be a flat mirror of TOML. It should organize GEPA setup
by conceptual ownership:

    GepaConfig
      run: RunSettings
      container: ContainerConnection
      taskset: TasksetSelection
      program: PromptProgram | None
      policy: PolicyConfig | None
      proposer: ProposerConfig
      objectives: ObjectiveConfig | None
      budgets: GepaBudgetConfig
      pipeline: GepaPipeline
      cache: CacheConfig
      outputs: OutputConfig

Each section should declare whether it is essential, optional, or discoverable.
That lets the SDK validate the smallest useful config while still supporting
more explicit production runs.

Section requirements:

    Essential
      container
      taskset
      proposer

    Essential unless discoverable from container
      program

    Essential unless owned by container
      policy

    Optional with defaults
      run
      objectives
      budgets
      pipeline
      cache
      outputs

`program` is the most important example. The user should not always have to
declare the mutable prompt program in Python config. If `program` is `None`,
GEPA discovers the program from the container contract:

    config = GepaConfig(
        container=ContainerConnection("http://127.0.0.1:8765"),
        taskset=TasksetSelection(train_ids=[...], heldout_ids=[...]),
        program=None,
        policy=None,
        proposer=ProposerConfig.codex_app_server(model="gpt-5.4-nano"),
    )

If the config supplies `PromptProgram`, it is an explicit override or offline
authoring path. If `program` is `None`, validation should check that the
container advertises/provides the program contract before the run starts.

OptimizerRun

Generic execution wrapper. It should not know GEPA internals directly beyond a
protocol or base type that can render a normalized optimizer request.

Responsibilities:

- Accept an optimizer config object, not a raw path.
- Execute locally through the existing Rust/PyO3 engine.
- Later, submit the same config to the standing optimizer service.
- Return a typed OptimizerRunResult with common fields: run_id, status,
  manifest_path, artifact paths, best_candidate, objective values, usage, and
  errors.

Sketch:

    class OptimizerRun:
        def __init__(self, config: OptimizerConfig): ...
        def execute(self) -> OptimizerRunResult: ...
        def submit(self, service_url: str) -> OptimizerRunHandle: ...

OptimizerConfig

Base protocol for optimizer-specific configs.

Responsibilities:

- Know optimizer name/version.
- Validate itself.
- Render normalized config for Rust/service execution.
- Serialize to TOML or JSON for reproducibility.

Sketch:

    class OptimizerConfig(Protocol):
        optimizer: str
        def validate(self) -> None: ...
        def to_dict(self) -> dict[str, Any]: ...
        def to_toml(self, path: str | Path | None = None) -> str: ...

GepaConfig

GEPA-specific config object. This is where `from_toml()` belongs.

Responsibilities:

- Parse existing TOML into typed SDK objects.
- Preserve round-trip ability for current TOML configs.
- Provide named fields for GEPA concepts instead of leaking raw TOML section
  names into user code.
- Render the current Rust TOML shape as a compatibility projection.

Sketch:

    class GepaConfig:
        @classmethod
        def from_toml(cls, path: str | Path) -> GepaConfig: ...
        @classmethod
        def from_dict(cls, data: Mapping[str, Any]) -> GepaConfig: ...
        def validate(self) -> None: ...
        def to_legacy_toml_dict(self) -> dict[str, Any]: ...
        def to_toml(self, path: str | Path | None = None) -> str: ...

Naming direction

Current TOML names should not necessarily become the SDK names:

- `[dataset] train_seeds` should become a taskset or dataset selection object
  with `train_ids` / `heldout_ids` or eventually `task_ids`.
- `[candidate]` plus `[seed_candidate]` should become a `PromptProgram`.
- `[container] url` should become `ContainerConnection`. `[container] command`
  is legacy TOML compatibility, not the SDK config shape.
- `[gepa] selection_objective`, `objective_keys`, `objective_directions`, and
  `objective_acceptance` should become `ObjectiveConfig`.
- `[gepa] max_total_rollouts` should sit under `GepaBudgetConfig`.
- `[gepa.pipeline.*]` should sit under `GepaPipeline`.

Objective language

Do not name the SDK section with the old generic evaluation wording. The SDK
should consistently use objective language. Rust already has the right
conceptual model:

- `ObjectiveSetRecord`
- `ObjectiveSpec`
- `selection_objective`
- `objective_keys`
- `objective_directions`
- `GepaObjectiveAcceptanceConfig`

Reward is not a separate top-level SDK section. Reward is the default observed
objective signal from rollout frames. In Rust today, when a sensor frame does
not provide explicit objective values, it is projected into an objective named
`outcome_reward` sourced from `sensor_frame.reward`. The SDK should expose that
as the default objective, while allowing containers to return richer objective
values.

Sketch:

    objectives=ObjectiveConfig.reward(
        name="outcome_reward",
        direction="maximize",
        source="container.rollout.reward",
    )

Multi-objective sketch:

    objectives=ObjectiveConfig(
        selection_objective="task_success",
        frontier_type="per_example_objective",
        objectives=[
            Objective.reward("task_success", direction="maximize"),
            Objective.metric("latency_penalty", direction="minimize"),
        ],
        acceptance=ObjectiveAcceptance(
            criterion="protected_objective_guard",
            protected_objectives=["task_success"],
            objective_regression_tolerance=0.02,
        ),
    )

Like `program`, objectives can be SDK-authored or discovered. If `objectives` is
`None`, GEPA should first use objective metadata from the container contract when
available. If neither config nor container declares objectives, GEPA falls back
to the default reward objective.

Essential versus optional fields

The SDK should avoid forcing users to provide values GEPA can safely default or
discover.

RunSettings

- Optional.
- Defaults: generated run id, output directory under `runs/`, deterministic seed
  default.
- User supplies when they need reproducibility, stable artifact paths, or
  service-visible run names.

ContainerConnection

- Essential.
- The optimizer ultimately needs a URL for a running container.
- `GepaConfig` should only accept `ContainerConnection`, not `ContainerHandle`
  and not `ContainerLaunch`.
- If the user launches through `synth_containers`, the returned handle must be
  converted to a connection before building the GEPA config.
- Launch command, cwd, env, port, startup timeout, logs, and cleanup are
  container/runtime lifecycle details, not GEPA algorithm details.

TasksetSelection

- Essential.
- Must specify what train/heldout tasks to evaluate.
- Current TOML uses split names and seed arrays; SDK should express this as task
  ids / example ids and render the legacy fields as needed.

PromptProgram

- Essential unless provided by the container.
- Explicit SDK form is useful for local authoring, offline config generation, and
  tests.
- `None` is preferred when the container is the source of truth for mutable
  fields, seed prompt values, and program metadata.
- GEPA should fail early if neither config nor container supplies a program.

PolicyConfig

- Essential only when the optimizer run supplies rollout policy settings.
- Optional when the container owns its own policy/model/credentials.
- `None` means the container is policy-ready and GEPA should not inject a policy
  override.
- Explicit `PolicyConfig` means the optimizer run supplies the rollout policy
  settings to the container.
- API keys should be referenced by env var name, not embedded.
- Validation should fail early if `policy=None` and the container contract does
  not advertise that it owns a runnable policy.

Current code evidence:

- `synth_containers.http_models.RolloutRequestModel.policy` is already optional.
  This means the HTTP contract can support container-owned policy.
- Rust `SynthOptimizerConfig.policy` is currently always defaulted and GEPA
  serializes it into rollout payloads. That is a compatibility behavior, not the
  desired SDK shape.
- The service OpenAPI currently requires `policy`; that should be relaxed or
  represented as `policy: null` when the container owns policy execution.

PolicyType

Add an enum for the control shape of the container-owned or optimizer-supplied
policy. This is not the provider API family. `api_family` says "OpenAI chat vs
responses"; `policy_type` says what kind of agent/control loop is being run.

Sketch:

    class PolicyType(StrEnum):
        DAG = "dag"
        REACT = "react"
        CODEX = "codex"

    class PolicyConfig:
        policy_type: PolicyType = PolicyType.REACT
        provider: str | None = None
        model: str | None = None
        api_family: str | None = None
        credential_env: str | None = None
        config: dict[str, Any] = {}

Suggested meanings:

- `DAG`: fixed graph or pipeline policy; useful when candidate fields configure
  nodes, prompts, routers, or evaluators in a deterministic graph.
- `REACT`: iterative observe/act policy, typically tool- or action-mediated.
- `CODEX`: stateful Codex-session policy with workspace/session semantics.

Container-owned policy should advertise at least:

    policy_ready: true
    policy_type: "react" | "dag" | "codex"
    policy_roles: [...]
    policy_override_supported: true | false

If `policy=None`, GEPA should pass no policy override on rollout requests and
should rely on the container's advertised policy contract. If `policy` is
provided, GEPA can include the explicit policy override in rollout payloads.

ProposerConfig

- Essential.
- Defines the reflection/proposal backend and model.
- Should remain separate from rollout policy; they are different roles.

ObjectiveConfig

- Optional with defaults.
- Defaults to the reward objective.
- Needed for multi-objective optimization, non-default objective direction,
  protected objectives, and objective acceptance policy.

BudgetConfig / GepaBudgetConfig

- Optional with defaults.
- Needed for cost/time/rollout limits and train/heldout split budgets.
- Budgeting should have a shared base class because every optimizer needs
  common stopping limits, while each optimizer can extend it with
  algorithm-aware fields.

Sketch:

    class BudgetConfig:
        max_cost_usd: float | None = None
        max_time_seconds: int | None = None
        max_total_rollouts: int | None = None
        max_prompt_tokens: int | None = None
        max_completion_tokens: int | None = None
        max_total_tokens: int | None = None

    class GepaBudgetConfig(BudgetConfig):
        train_rollouts: int | None = None
        heldout_rollouts: int | None = None
        no_improvement_generations: int | None = None
        reward_threshold: float | None = None

The base budget should describe global resource limits. `GepaBudgetConfig`
should describe how GEPA allocates those limits across seed train, minibatch,
full-train, proposer, and heldout phases. A future optimizer can subclass or
compose the same base with its own phase-specific fields.

GepaPipeline

- Optional with defaults.
- Needed for candidate fanout, worker counts, adaptive rollout concurrency, and
  other throughput controls.

CacheConfig

- Optional.
- Defaults can use a per-run cache or no cache depending on the final SDK
  policy. Users opt in for reproducibility or repeated local runs.

OutputConfig

- Optional.
- Controls manifest paths, normalized event output, charts, and reporting.

Compatibility boundary

Rust remains the execution source of truth for now. The Python SDK should not
reimplement GEPA. Instead:

1. Python SDK constructs and validates typed config.
2. SDK renders the normalized legacy TOML/dict shape.
3. PyO3 passes that config to the Rust GEPA executor.
4. Rust returns the same artifact/result data.
5. Python wraps result data in typed result objects for downstream examples.

Container launch boundary

Today there are two supported shapes:

1. SDK target shape: `GepaConfig` contains only a `ContainerConnection`, and
   GEPA connects to an already-running container URL.
2. Legacy TOML compatibility: old generated TOML may still contain
   `container.command`, and Rust GEPA can still start it through
   `ManagedContainerProcess` until examples migrate.

The long-term SDK should be URL-only from GEPA's perspective. Container
lifecycle belongs in the containers SDK, and handles should be converted before
building GEPA config:

    from synth_containers import ContainerRunner
    from synth_optimizers import OptimizerRun
    from synth_optimizers.gepa import GepaConfig

    handle = ContainerRunner.from_app("banking77_synth_gepa_dev:app").start()
    connection = handle.connection()
    config = GepaConfig(
        container=connection,
        taskset=TasksetSelection(train_ids=[...], heldout_ids=[...]),
        program=None,
        objectives=None,
        policy=None,
        proposer=ProposerConfig.codex_app_server(model="gpt-5.4-nano"),
    )
    result = OptimizerRun(config).execute()
    handle.stop()

The SDK can still offer a convenience wrapper that owns both pieces:

    with ContainerRunner.from_command([...]).start() as container:
        config = base_config.with_container(container.connection())
        result = OptimizerRun(config).execute()

This keeps GEPA algorithm-neutral about how containers are launched. GEPA only
needs a verified `ContainerConnection` and the discovered contract. The
container SDK can own port selection, process cleanup, Docker support, hosted
containers, local FastAPI apps, and future non-Python runtimes.

GEPA-AI compatibility

The Banking77 `gepa-ai` comparison does not show a TOML config. It configures
GEPA through a Python call:

    gepa.optimize(
        seed_candidate={field: seed_prompt},
        trainset=train_examples,
        valset=heldout_examples,
        adapter=DefaultAdapter(
            model=policy_model,
            evaluator=evaluator,
            max_litellm_workers=workers,
        ),
        reflection_lm=proposer_model,
        reflection_minibatch_size=minibatch_size,
        max_metric_calls=max_metric_calls,
        run_dir=output_dir,
        seed=0,
    )

That maps cleanly to the proposed SDK sections:

    GEPA-AI optimize arg        Synth SDK section
    seed_candidate             program.seed
    trainset / valset          taskset train / heldout selection
    adapter.model              policy.model
    adapter.evaluator          container rollout objective/reward contract
    max_litellm_workers        pipeline rollout worker count
    reflection_lm              proposer.model
    reflection_minibatch_size  pipeline minibatch size
    max_metric_calls           GepaBudgetConfig max_total_rollouts
    run_dir                    run/output settings
    seed                       run seed

If GEPA-AI has a stable TOML format, `GepaConfig.from_gepa_ai_toml(path)` is a
reasonable compatibility constructor. It should be an adapter into our typed
config, not a second native config model. If the common GEPA-AI interface remains
Python kwargs, prefer a more direct adapter:

    GepaConfig.from_gepa_ai_kwargs(...)
    GepaConfig.from_gepa_ai_optimize_call(...)

Open design question: GEPA-AI's `adapter.evaluator` is an in-process Python
callable, while Synth GEPA normally evaluates through container rollouts. A
compatibility adapter can translate datasets, seed prompts, policy/proposer
models, budgets, and pipeline knobs, but it cannot automatically convert an
arbitrary evaluator callable into a container. For full migration, the evaluator
logic should live behind the container rollout/objective contract.

Target example: Banking77

Banking77 is a single-stage classifier container. The policy is owned by the
container: it reads its model/key/concurrency from container startup config and
uses the candidate prompt during `/rollout`. GEPA does not need a policy override.

Python SDK shape:

    from synth_containers import ContainerRunner
    from synth_optimizers import OptimizerRun
    from synth_optimizers.config import CacheConfig, RunSettings, TasksetSelection
    from synth_optimizers.gepa import GepaBudgetConfig, GepaConfig, GepaPipeline
    from synth_optimizers.gepa import ProposerConfig

    with ContainerRunner.from_command(
        [
            "python",
            "banking77_synth_gepa_dev.py",
            "--serve",
        ],
        env={
            "BANKING77_TRAIN_SAMPLE": "12",
            "BANKING77_TEST_SAMPLE": "12",
            "BANKING77_POLICY_MODEL": "gpt-4.1-nano",
            "BANKING77_POLICY_CONCURRENCY": "16",
        },
    ).start() as container:
        config = GepaConfig(
            run=RunSettings(run_id="banking77_dev", output_dir="runs/banking77_dev"),
            container=container.connection(),
            taskset=TasksetSelection(
                train_split="train",
                heldout_split="test",
                train_ids=list(range(12)),
                heldout_ids=list(range(4)),
            ),
            program=None,
            objectives=None,
            policy=None,
            proposer=ProposerConfig.codex_app_server(
                model="gpt-5.4-nano",
                api_key_env="OPENAI_API_KEY",
            ),
            budgets=GepaBudgetConfig(max_total_rollouts=80),
            pipeline=GepaPipeline(
                max_generations=1,
                proposals_per_generation=2,
                minibatch_size=4,
            ),
            cache=CacheConfig.readwrite("runs/banking77_dev/cache.sqlite"),
        )
        result = OptimizerRun(config).execute()

    minibatch_size = 4

Notably absent:

- No `[policy]`: the container owns policy execution.
- No `[candidate]` / `[seed_candidate]`: the container provides the program.
- No `[objectives]`: GEPA discovers objectives or falls back to reward.
- No `[container.command]`: container launch is owned by `synth_containers`.

The container contract should advertise roughly:

    policy_ready = true
    policy_type = "dag"
    policy_override_supported = true

`policy_type="dag"` fits Banking77 because rollout is a fixed one-call
classification pipeline, not an iterative ReAct loop.

Target example: TBLite

TBLite is also container-policy-owned. The container runs a fixed coding pipeline:
candidate prompt + task spec -> model output -> pytest verifier -> reward. The
policy type is also `dag` unless/until the container becomes a multi-turn coding
agent.

- No `[policy]`: TBLite owns its model call.
- No explicit program: the container provides `starting_prompt`.

- No launch command in GEPA config: launch belongs to `synth_containers`.

Package layout

Proposed package split:

    src/synth_optimizers/
      __init__.py
      cli.py
      _synth_optimizers.pyi
      run.py
      types.py
      gepa/
        __init__.py
        config.py
        program.py
        container.py
        result.py

Suggested imports:

    from synth_optimizers import OptimizerRun
    from synth_optimizers.gepa import GepaConfig, GepaBudgetConfig, GepaPipeline

Avoid:

    from synth_optimizers import GepaRun

`GepaRun` can remain temporarily as a backwards-compatible alias or shim, but it
should stop being the primary documented API.

Migration path

1. Add SDK classes without changing Rust execution.
2. Make `GepaConfig.from_toml()` parse existing Banking77/MiniGrid/TBLite TOML.
3. Add `OptimizerRun(GepaConfig.from_toml(...)).execute()`.
4. Update dev examples to build configs through `GepaConfig`.
5. Keep raw `synth-optimizers gepa run --config ...` as CLI compatibility.
6. Deprecate direct `GepaRun.from_toml()` documentation after examples migrate.
